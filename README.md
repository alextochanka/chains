## Цель работы

Научиться реализовывать и интегрировать механизм консенсуса **Proof-of-Work (PoW)** в распределённую блокчейн-систему, понять:

- как PoW защищает сеть от спама и атак;
- как обеспечивается честное добавление блоков;
- как уровень сложности влияет на скорость формирования цепочки;
- чем PoW отличается от правила «первый прислал — тот и прав».

---

## Теоретическая основа

**Proof-of-Work** — алгоритм консенсуса, при котором узел должен выполнить **вычислительно сложную, но легко проверяемую** задачу, чтобы добавить новый блок в цепочку.

В классическом виде задача формулируется так:

> Найти такое значение **nonce**, при котором хеш блока начинается с заданного количества нулей (например, 4 нуля в шестнадцатеричной записи → `0000...`).

Формула хеша блока:

```
hash = SHA256(index | timestamp | data | previous_hash | creator | nonce)
```

Поля разделяются символом `|`, чтобы избежать коллизий конкатенации.

### Что даёт PoW

- **Замедляет создание блоков** → спам и атаки становятся экономически невыгодными.
- **Гарантирует, что только один узел** (первый решивший задачу) добавит блок.
- **Требует от всех узлов** независимой проверки корректности nonce.
- В отличие от правила «первый прислал — тот и прав», PoW делает **невозможным мгновенное** создание блока — требуется время и вычисления.

## Что реализовано

### Шаг 1: Модификация класса `Block`

Добавлено поле **`nonce`** (целое число, подбирается при майнинге).

Функция `calculate_hash` обновлена — теперь включает `nonce` в хешируемые данные.

### Шаг 2: Метод `mine_block(difficulty)`

```python
def mine_block(self, difficulty, should_stop=None):
    target = "0" * difficulty
    self.nonce = 0
    start = time.time()
    while True:
        if should_stop is not None and should_stop():
            raise InterruptedError("Майнинг прерван")
        self.hash = calculate_hash(...)
        if self.hash.startswith(target):
            break
        self.nonce += 1
    return time.time() - start
```

Параметр `should_stop` позволяет **прервать майнинг** при остановке узла.

### Шаг 3: Обновление класса `Blockchain`

- Добавлено поле **`difficulty`** (по умолчанию 4).
- `add_block(data)` теперь **майнит** блок перед добавлением и возвращает `(block, elapsed)`.
- `is_block_valid` проверяет:
  1. PoW — хеш начинается с `difficulty` нулей;
  2. Целостность — пересчёт хеша совпадает с `block.hash`;
  3. Связь с предыдущим блоком.
- `is_valid` — полная проверка цепочки (PoW + связи + порядок индексов).
- `replace_chain` — разрешение форков: побеждает **более длинная** цепочка; при равной длине — с **меньшим хешем** последнего блока.

### Шаг 4: Модификация класса `Node`

- `create_block(data)` — сначала **майнит** блок локально, затем рассылает.
- После майнинга проверяет, не продвинулась ли цепочка — если да, свой блок **отбрасывается**.
- `receive_block(block)` — проверяет PoW через `is_block_valid`.
- Кэш `known_hashes` подавляет обработку дубликатов.
- При обнаружении форка узел рассылает `get_chain` и заменяет свою цепочку, если у пира она сильнее.

- 3 узла, `difficulty = 4`.
- Сценарий 1 — одиночный майнинг.
- Сценарий 2 — гарантированный форк + разрешение по правилу «самая длинная цепочка / меньший хеш».

## Сценарии демонстрации

### Сценарий 1: одиночный майнинг

```
Node_1 майнит блок #1 «Транзакция А»
Node_1 → broadcast → Node_2, Node_3
Node_2, Node_3 принимают блок
```

Результат: у всех трёх узлов **одинаковая** цепочка `[genesis, #1]`, `is_valid = True`.

### Сценарий 2: гонка майнеров

Node_1 и Node_2 **одновременно** начинают майнить блок #2. Возможны два исхода:

1. **Побеждает один** — второй отбрасывает свой блок, потому что цепочка уже продвинулась.
2. **Форк** — оба добавили свой блок. Разрешается правилом:
   - побеждает более длинная цепочка;
   - при равной длине — цепочка с **меньшим** хешем последнего блока.

После разрешения форка все три узла сходятся на одной ветке.

### Визуализация

Функция `visualize_chain` рисует блоки всех узлов:

- цвет = создатель блока;
- подпись = `#index`, `creator`, `n=nonce`;
- стрелки = связь по `previous_hash`.

## Проверка защиты от подделки (Шаг 6)

В `main()` после сценариев выполняется:

1. **Изменение данных** в блоке #1:
   ```python
   target.data = "ПОДДЕЛКА!"
   target.recalculate_hash()   # nonce старый, хеш пересчитан
   ```
2. Проверка `is_valid()` → **False**: хеш не начинается с `difficulty` нулей.
3. **Попытка перемайна** подделки:
   ```python
   target.mine_block(DIFFICULTY)
   ```
   Даже после успешного перемайна блока #1, `is_valid()` остаётся **False**, потому что следующий блок #2 ссылается на **старый** хеш #1. Чтобы обмануть сеть, нужно перемайнить **всю** цепочку начиная с изменённого блока — а это **вычислительно дорого** (растёт экспоненциально с числом блоков).

## Ответы на контрольные вопросы

### 1. Почему PoW делает атаку 51% дорогостоящей? Что именно должен контролировать злоумышленник?

Атака 51% — это попытка **переписать историю**: заменить уже принятые блоки на альтернативные. Чтобы сеть приняла альтернативную цепочку, она должна быть **длиннее** (иметь больше суммарной работы) текущей честной цепочки.

**Что контролирует злоумышленник:** не «половину узлов», а **более половины суммарного хешрейта** сети. Каждый блок в его цепочке требует такого же объёма хеширования, как у честных майнеров. Чтобы догнать и обогнать честную цепочку, ему нужно **выдавать больше хешей в секунду**, чем вся остальная сеть вместе взятая.

**Стоимость:**
- оборудование (ASIC-фермы);
- электроэнергия;
- упущенная выгода от честного майнинга.

Именно поэтому атака 51% на крупные сети **экономически бессмысленна**.

### 2. Как уровень сложности влияет на время добавления блока и безопасность сети?

Вероятность попасть в условие PoW при одном хеше: `p = 16^(-difficulty)`. Среднее число попыток: `16^difficulty`. Значит, **время майнинга растёт экспоненциально** — каждый лишний ноль увеличивает его **в 16 раз**.

| difficulty | среднее время (наш код) |
|-----------|-------------------------|
| 4 | 0.05–0.5 с |
| 5 | 1–3 с |
| 6 | 16–30 с |
| 7 | 4–8 мин |

**Безопасность** растёт так же: чтобы заменить `k` блоков, атакующему нужно выполнить работу, эквивалентную `k · 16^difficulty` хешей. Чем выше difficulty, тем **дороже** атака.

**Обратная сторона:** слишком высокий difficulty замедляет подтверждение транзакций и увеличивает время до финальности. В реальных сетях difficulty **автоматически регулируется** (Bitcoin — каждые 2016 блоков), чтобы среднее время блока оставалось стабильным.

### 3. Почему в PoW важно, чтобы задача была трудной для решения, но лёгкой для проверки?

**Трудность для решения** нужна, чтобы:
- спам и атаки были дорогими;
- блоки появлялись с предсказуемым интервалом;
- обогнать честную сеть было вычислительно невозможно.

**Лёгкость для проверки** нужна, чтобы:
- **любой узел** мог проверить блок за миллисекунды (один вызов SHA-256);
- сеть могла **быстро синхронизироваться** — новый узел проверяет всю цепочку за секунды;
- не требовалось **доверять** майнеру — узел сам пересчитывает хеш.

Асимметрия «трудно / легко» — фундамент PoW. Если бы проверка была такой же дорогой, как майнинг, сеть не смогла бы работать.

### 4. Какие недостатки у PoW по сравнению с другими алгоритмами консенсуса (например, PoS)?

| Критерий | PoW | PoS |
|----------|-----|-----|
| Энергопотребление | Огромное | Ничтожное |
| Пропускная способность | Низкая | Высокая |
| Время финальности | ~час (6 подтверждений) | секунды–минуты |
| Оборудование | ASIC → централизация | обычные серверы |
| Атака 51% | дорогая, но возможна | дорогая, но есть «nothing-at-stake» |
| Экология | плохо | хорошо |

Дополнительные минусы PoW:
- централизация майнинга (крупные пулы);
- «пустые» блоки для быстрой награды;
- selfish mining;
- зависимость от цены монеты (падение цены → уход майнеров → падение безопасности).

Плюсы PoW: проверенная временем безопасность (Bitcoin с 2009), простота проверки, отсутствие требования доверять крупным держателям монет.

### 5. Можно ли использовать CRC32 вместо SHA-256 в PoW?

**Нет, нельзя.**

CRC32 — это **контрольная сумма**, а не криптохеш. Её свойства:

- **линейность**: `CRC(A ⊕ B) = CRC(A) ⊕ CRC(B)`;
- **обратимость**: по CRC легко восстановить часть данных;
- **коллизии за секунды**: 32 бита → коллизия после ~2^16 попыток;
- **нет лавинного эффекта**.

Для PoW это означает:

- **Майнинг тривиален** — nonce вычисляется аналитически, без перебора;
- **проверка ломается** — злоумышленник подделает данные и тут же подберёт CRC под нужный префикс;
- **защита исчезает** — 32-битного пространства катастрофически мало.

| Свойство | SHA-256 | CRC32 |
|----------|---------|-------|
| Односторонность | ✅ | ❌ |
| Устойчивость к коллизиям | 2^128 | 2^16 |
| Лавинный эффект | ✅ | ❌ |
| Нелинейность | ✅ | ❌ |
| Размер | 256 бит | 32 бита |

CRC32 годится для **обнаружения случайных ошибок** при передаче, но **не для криптографии** и тем более не для PoW.
